===============================================================================
CODELENS AI — AI FRONTEND CODE REVIEWER
Project requirements & technical specification
===============================================================================

Source brief
------------
"AI Frontend Code Reviewer. Highly relevant to a React/Next.js background;
demonstrates AI integration without requiring a large backend. Naturally
showcases streaming, markdown rendering, syntax highlighting, file uploads,
authentication, prompt engineering, and frontend performance."

Target resume line
------------------
"Built an AI-powered code review platform with real-time streaming analysis,
syntax highlighting, and actionable recommendations for performance,
accessibility, and React best practices."


-------------------------------------------------------------------------------
1. FUNCTIONAL REQUIREMENTS
-------------------------------------------------------------------------------

FR-1   INPUT
       1.1  Paste code directly into an in-browser editor.
       1.2  Upload one or more files via picker or drag-and-drop.
       1.3  Upload a .zip archive; extract in-browser, skipping node_modules,
            build output and minified bundles.
       1.4  Accept .js .jsx .ts .tsx .mjs .cjs .css .scss .html .vue .svelte
            .json
       1.5  Enforce limits: 256KB per file, 1MB per review, 20 files max.
       1.6  Multi-file workspace with tabs; per-file finding counts.

FR-2   ANALYSIS
       2.1  Six review lenses: performance, accessibility, React best
            practices, security, maintainability, correctness.
       2.2  Local deterministic rule pass runs on paste, before any network
            request, and returns findings in under ~5ms.
       2.3  AI pass streams from Claude (claude-opus-5) via a server route.
       2.4  Local findings are merged with AI findings and de-duplicated by
            (file, category, line ± 3); the AI finding wins because it carries
            a concrete fix.
       2.5  Three review depths — quick / standard / thorough — mapped to
            model reasoning effort.
       2.6  Optional per-category emphasis and free-text author context.

FR-3   STREAMING  (core requirement)
       3.1  Findings appear individually as they are produced, not in one
            batch at the end.
       3.2  Model reasoning streams into a separate collapsible panel.
       3.3  A running phase indicator: analysing → reasoning → writing.
       3.4  Cancel mid-stream; cancellation aborts the upstream model request.
       3.5  Graceful degradation: a malformed record is dropped, not fatal.

FR-4   FINDINGS
       4.1  Each finding carries: severity, category, file, line, title,
            description, impact, suggested fix, confidence.
       4.2  Severity ladder: critical / high / medium / low / info.
       4.3  Before/after diff for each suggested fix.
       4.4  One-click "Apply fix" patches the editor in place.
       4.5  Clicking a finding reveals and highlights its line in the editor.
       4.6  Coloured severity markers in the editor gutter.
       4.7  Filter by severity, category and free text.

FR-5   SCORING
       5.1  0–100 quality score, severity-weighted and normalised against
            file volume so large files are not unfairly penalised.
       5.2  Letter grade A–F derived from the score.
       5.3  Animated score dial, honouring prefers-reduced-motion.

FR-6   NO AUTHENTICATION  (deliberate)
       6.1  The product has no sign-in, no accounts and no sessions. Every
            route is open.
       6.2  Rationale: all state — files, review history, settings — lives in
            the visitor's own browser. There is no server-side record of any
            of it, so a login would authenticate a user against their own
            localStorage: a gate with nothing behind it.
       6.3  Consequences, all intended:
            - no password store, user table, session secret or OAuth client
              secret exists, so none can leak
            - /dashboard /review /history /settings are statically
              prerendered rather than server-rendered per request
            - no edge middleware is needed; proxy.js is removed
            - nothing stands between a first-time visitor and the product
       6.4  Authentication is reintroduced only alongside a backend that has
            something real to protect.

       Built and then deliberately removed: email/password accounts in
       localStorage with PBKDF2 hashing and a self-signed session token; a
       canvas captcha; a stateless server-verified email code flow; and a
       genuine Google OAuth 2.0 integration via Auth.js. Each worked. None
       protected anything, so all were deleted along with next-auth,
       crypto-js and js-cookie.

FR-7   HISTORY & DASHBOARD
       7.1  Every completed review is saved (most recent 50).
       7.2  Dashboard: average score, score trend, findings by category,
            findings by severity, recent reviews.
       7.3  History list with search, open and delete.
       7.4  Review detail page; reopen a past review in the workspace.

FR-8   EXPORT
       8.1  PDF report with cover block, severity table and findings table.
       8.2  Markdown report.
       8.3  JSON (machine-readable, suitable for a CI gate).
       8.4  Zip containing the report plus the reviewed source.

FR-9   UX
       9.1  Command palette (Cmd/Ctrl+K).
       9.2  Cmd/Ctrl+Enter runs or cancels a review.
       9.3  Light / dark / system theme.
       9.4  Resizable editor and results panes.
       9.5  Responsive from 360px upward.
       9.6  Toast notifications for every outcome.


-------------------------------------------------------------------------------
2. NON-FUNCTIONAL REQUIREMENTS
-------------------------------------------------------------------------------

NFR-1  THE DEMO MUST NEVER DEAD-END
       With no API key configured, the identical pipeline runs against the
       local analysis engine — same SSE envelope, same records, same client
       code path. A visitor without a key sees a complete working product.

NFR-2  SECURITY
       - The Anthropic key lives server-side only; never sent to the browser.
       - Optional bring-your-own key is stored in the user's own browser,
         sent per request over HTTPS, never persisted or logged server-side.
       - Content-Security-Policy, X-Content-Type-Options, Referrer-Policy,
         X-Frame-Options, Permissions-Policy set on every response.
       - Every request body validated with a zod schema before use.
       - Per-IP rate limiting on the review endpoint.
       - No password store and no user database; Google is the sole identity
         provider and its client secret never leaves the server.
       - Session is a signed, expiring JWT, decoded and signature-checked at
         the edge before a protected page renders.
       - Post-login redirects constrained to same-site paths.
       - Provider errors are mapped to safe messages — no internals leak.

NFR-3  ACCESSIBILITY
       - Keyboard operable throughout; visible focus ring on every control.
       - Skip-to-content link as the first tab stop.
       - Labels, roles and aria-describedby on all form fields.
       - Validation errors announced via role="alert".
       - Streaming status announced via aria-live.
       - prefers-reduced-motion respected by every animation.
       - Charts never rely on colour alone — legends and labels throughout.

NFR-4  PERFORMANCE
       - Monaco, the diff viewer, JSZip, jsPDF and file-saver are all loaded
         on demand, never in the initial bundle.
       - Editor writes are debounced.
       - React Compiler enabled.
       - Derived values computed during render rather than synced via effects.

NFR-5  RELIABILITY
       - Route-level error boundary.
       - Model output is normalised and type-coerced before it reaches the UI.
       - Refusal and truncation responses handled explicitly.
       - Streams recover from partial or malformed lines.

NFR-6  CODE QUALITY
       - JavaScript only — no TypeScript.
       - Zero ESLint errors and zero build warnings.
       - Prettier-formatted.
       - No test suite (explicitly out of scope).

4. ENVIRONMENT
-------------------------------------------------------------------------------

All values optional. With no .env.local the app runs in demo mode and every
feature still works.

  ANTHROPIC_API_KEY             Server-side key. Enables live review.
  ANTHROPIC_MODEL               Default: claude-opus-5
  ANTHROPIC_EFFORT              low | medium | high | xhigh | max
  NEXT_PUBLIC_ALLOW_BYO_KEY     Allow visitor-supplied keys. Default: true
  NEXT_PUBLIC_FORCE_DEMO_MODE   Force the local engine. Default: false
  NEXT_PUBLIC_SITE_URL          Canonical URL for metadata.

6. ACCEPTANCE CRITERIA
-------------------------------------------------------------------------------

  [x] npm run build completes with zero errors and zero warnings
  [x] npm run lint reports zero errors and zero warnings
  [x] Every route returns 200; unknown routes return 404
  [x] Every app route is reachable with no account; no auth route exists

      editor if it cannot load, rather than an endless spinner
  [x] Exactly one editor instance mounts at any viewport width

  [x] Security rules fire on hardcoded secrets, dangerouslySetInnerHTML,
      eval, and target="_blank" without rel="noopener"
  [x] Applying a suggested fix patches the editor in place
  [x] PDF, Markdown, JSON and Zip exports all produce valid files
  [x] No TypeScript files; no test files
